# Contributing

## Where to edit

- Page content: `src/pages/`
- Shared layout and form rendering: `src/components/`
- Shared and page-specific styles: `src/styles/`
- Browser behavior and local media: `src/assets/`
- Build metadata and page registration: `build.mjs`
- Operational guides: `docs/`

Do not edit `dist/` by hand; it is generated by the build.

## Local workflow

Use Node.js 20 or newer and the pnpm `12.9.1` version pinned in `package.json`.

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm build
```

Use `pnpm preview` to review the generated site at `http://127.0.0.1:4173`. Deployment changes also require `pnpm cloudflare:dry-run` and the checks described in the [deployment guide](/docs/DEPLOYMENT.md).

## Propose a change

1. Fork the public repository and clone your fork.
2. Create a focused topic branch from `development`:

   ```sh
   git switch development
   git switch -c topic/short-description
   ```

3. Make the change and run the relevant checks.
4. Open a pull request targeting `development`, with a concise summary and verification notes.

Maintainers review and accept contributions on `development`. An accepted revision is promoted to `main` separately; contributors should not target `main` for ordinary work or deploy the site.

## Review checklist

- Check narrow mobile and desktop layouts, including long text and touch targets.
- Confirm keyboard navigation, visible focus, headings, labels and meaningful alternative text.
- For progressive enhancements such as service tabs, confirm the underlying content remains available without JavaScript.
- Preserve approved names, quotes, prices, form IDs and historic-cost disclaimers exactly.
- Publish testimonials only from owner-supplied, approved wording.
- Keep links, both Tally fallbacks and the branded 404 valid.
- Update each meaningfully edited Markdown file's Asia/Tokyo timestamp and validate its repository-root links.

## Branch and release flow

Changes are reviewed on `development`. The owner accepts the exact revision before promotion to `main`, and production release is a separate manager-authorized local Wrangler deployment from accepted `main`. A push or a successful local build is not deployment authority.

GitHub Actions is configured to check pushes and pull requests to `development` and `main`; inspect the actual run rather than assuming it passed.

## Data and access boundaries

Never commit credentials, Wrangler account details, DNS exports, private customer records or Tally responses. Public Tally form IDs are build configuration, but form submissions and Tally account changes are outside normal repository work. Do not change access, branch protection, DNS, production services or the [MIT License](/LICENSE) terms without explicit owner authorization.
